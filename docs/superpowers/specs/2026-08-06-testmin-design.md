## 1. 제품 정의

한국형 "고사(考査)" 컨셉으로 5종의 테스트를 하나의 앱에 묶는다. 모든 문항에 **정답 또는 유형 판정의 근거를 해설로 제공**하는 것이 이 앱의 차별점이다.

### 1.1 5개 카테고리

| 카테고리 | 종류 | 출제 문항 | 결과물 |
|---|---|---|---|
| IQ 고사 | 정답형 | 20 (생성 12 + 수기 8) | 급수 합격증 + 추정 점수 |
| 성격 16유형 고사 | 유형형 | 24 (4축 × 6) | 4글자 코드 + 자체 별명 카드 |
| MZ 고사 | 정답형 | 15 | 급수 합격증 |
| 사투리 고사 | 정답형 | 12 (지역 선택) | 지역별 급수 합격증 |
| 심리 테스트 | 유형형 | 12 × 3종 | 유형 카드 |

사투리 지역: 경상 · 전라 · 충청 · 강원 · 제주 · 서울경기 (6개). **지역별로 급수가 따로 매겨진다.**

심리 테스트 3종: 연애 성향 / 스트레스 반응 / 소통 유형. 각각 **5개 유형 중 하나**로 분류한다.

### 1.2 두 갈래 해설 모델

요청 사항인 "각 문제의 정답과 이유"는 테스트 종류에 따라 두 형태로 구현한다.

- **정답형(scored)** — "왜 이것이 정답인가". 정답 근거 + 매력적인 오답이 왜 틀렸는지.
- **유형형(typed)** — "이 문항이 어느 축을 쟀고, 당신의 응답이 그 축을 어느 쪽으로 얼마나 밀었는가".

두 경우 모두 결과 화면에서 문항별로 열람 가능하며, 정답형은 오답노트에 누적된다.

### 1.3 결과 = 공유 대상

정답형 결과는 **급수 합격증** 카드, 유형형 결과는 **유형 카드**로 렌더링된다. 이 카드가 그대로 이미지로 캡처되어 시스템 공유시트로 나간다. 이 앱이 확산되는 유일한 경로이므로 결과 카드는 1급 우선순위 UI다.

### 1.4 상표·저작권 정책 (확정)

**사용하지 않는다:**
- "MBTI" — The Myers-Briggs Company 등록상표. 앱 내부·스토어 제목·설명·스크린샷 어디에도 쓰지 않는다.
- 실제 MBTI 문항지, 레이븐 누진행렬(Raven's Progressive Matrices), WAIS 등 표준화 검사도구의 문항을 인용하거나 변형하지 않는다.
- 16Personalities의 유형 별명("옹호자", "중재자" 등) — NBI 상표.
- "당신의 진짜 IQ는 OOO입니다" 식 단정 표현.

**사용한다:**
- "IQ" (일반명사), "성격 16유형", "MZ 고사", "사투리 고사", "심리 테스트"
- 융 이론 기반 4축(E/I · S/N · T/F · J/P)과 ENFP 형태의 4글자 코드 — 이론과 코드 표기 자체는 보호 대상이 아니다.
- 유형별 별명은 전부 자체 창작하고 코믹 톤으로 붙인다. (예: ENFP = "판 벌이고 수습 안 하는 사람")

**고지 문구:** IQ 고사와 심리 테스트 결과 화면 하단에 오락 목적임을 명시하는 고정 문구를 넣는다. 임상적·진단적 도구가 아님을 밝힌다.

**문항 출처 정책:** 모든 문항은 자체 창작한다. 사투리·MZ 항목은 국립국어원 자료 등으로 **사실 검증만** 하고 정의문을 그대로 옮기지 않는다(사실 자체에는 저작권이 없으나 표현에는 있다). 각 문항의 `source` 필드에 검증 근거를 기록한다.

- 본문 폰트로 Pretendard를 검토했으나 npm 배포본이 웹폰트(woff2) 위주라 RN이 쓰는 ttf를 안정적으로 얻기 어렵다. 같은 OFL이면서 npm 설치만으로 끝나고 한글 자소 커버리지가 더 넓은 Noto Sans KR로 정했다.

- **모든 폰트는 앱에 번들한다.** iOS 이식 시 폰트 차이로 레이아웃이 깨지지 않도록 시스템 폰트에 의존하지 않는다.
- 라이선스 원문을 `docs/licenses/`에 보관하고 설정 화면에 오픈소스 고지를 넣는다.

### 2.3 테마

**라이트 모드 고정.** 네오브루탈 팝은 크림 배경과 검정 테두리의 대비가 정체성이라 다크 모드에서 무너진다. 시스템 다크 설정을 따르지 않는다(`userInterfaceStyle: "light"`).

### 2.4 접근성

- 시스템 글자 크기 확대는 **최대 1.3배까지** 허용(`allowFontScaling` + `maxFontSizeMultiplier`). 그 이상은 두꺼운 테두리 레이아웃이 깨진다.
- 정답/오답은 색만으로 구분하지 않는다. 아이콘(⭕/❌)과 텍스트를 병기한다.
- 모든 터치 대상 최소 44×44dp.

### 3.2 권한 — v1은 0개

콘텐츠를 전량 앱에 내장하므로 **인터넷 권한을 포함해 어떤 권한도 선언하지 않는다.**

- 결과 카드는 캐시 디렉터리에 쓴 뒤 공유시트로 넘긴다 → 저장소 권한 불필요
- "갤러리에 저장"은 별도 기능으로 만들지 않는다. 공유시트에서 사용자가 갤러리 앱을 고르면 된다. 동일한 결과를 권한 0으로 얻는다.
- `expo-updates`(OTA)를 **넣지 않는다** — 인터넷 권한이 붙는다.
- **Expo prebuild가 생성하는 AndroidManifest에는 `INTERNET` 권한이 기본으로 들어간다.** `app.json`의 `android.permissions: []` 설정만으로는 제거되지 않으므로, `expo-build-properties` 또는 config plugin으로 `<uses-permission android:name="android.permission.INTERNET" tools:node="remove"/>`를 명시해 제거하고, 릴리스 AAB에서 `aapt2 dump permissions`로 실제 0개인지 검증한다.
- 결과: Play 데이터 안전 신고가 "수집 없음 / 공유 없음"으로 끝난다.

## 4. 콘텐츠 엔진

### 4.1 데이터 모델

```ts
type TestKind = 'scored' | 'typed';
type Axis = 'EI' | 'SN' | 'TF' | 'JP';

interface Choice {
  text?: string;              // 텍스트 선택지
  figure?: FigureSpec;        // IQ 도형 선택지 (SVG 스펙)
  weight?: number;            // typed 전용: -2 | -1 | +1 | +2
  why?: string;               // typed 전용: 이 선택이 뜻하는 것
}

interface Question {
  id: string;                 // "dialect-gs-0012", "iq-verbal-0007"
  kind: TestKind;
  prompt: string;
  figure?: FigureSpec;        // 문제 자체가 도형인 경우
  choices: Choice[];
  answerIndex?: number;       // scored 전용
  explanation?: string;       // scored 전용: 왜 이것이 답인가
  distractorNotes?: string[]; // scored 전용: 각 오답이 왜 틀렸는가 (선택)
  axis?: Axis | string;       // typed 전용
  difficulty: 1 | 2 | 3;
  tags?: string[];
  source?: string;            // 사실 검증 근거
}
```

**선택지 개수는 고정한다.** 텍스트 문항(사투리·MZ·언어유추·성격·심리)은 **4지선다**, IQ 도형·수열 문항은 **5지선다**로 한다. 도형 문제는 오답을 규칙 위반 방식별로 만들기 때문에 4개로는 매력적인 오답이 부족하다. 이 규칙은 콘텐츠 검증 스크립트가 강제한다.

`FigureSpec`은 SVG를 그리기 위한 **선언적 스펙**이지 SVG 문자열이 아니다. 도형 목록(종류·위치·회전·크기·채움)만 담고, 실제 렌더링은 `SvgFigure` 컴포넌트가 담당한다. 이렇게 분리하면 생성기가 렌더링을 몰라도 되고, 스펙만 비교하면 정답 유일성을 프로그램으로 검증할 수 있다.

### 4.2 IQ 문항 생성기

도형추리·행렬·수열은 **런타임에 시드 기반으로 생성**한다. 문제를 만든 규칙이 곧 해설이므로 해설이 틀릴 수 없고, 앱 용량을 쓰지 않으며, 재도전 때마다 새 문제가 나온다.

**시드 저장 = 문제 재현.** 오답노트에는 문항 전체가 아니라 `(generatorId, seed)`만 저장한다. 같은 시드는 항상 같은 문제를 만들어내므로 오답노트에서 정확히 그 문제를 복원할 수 있다.

**규칙 세트 (10종):**

1. 행렬 3×3 — 회전 진행 (행마다 90° 시계방향)
2. 행렬 3×3 — 요소 개수 증감
3. 행렬 3×3 — 채움/색 교대
4. 행렬 3×3 — 도형 합성 (A + B = C, XOR/AND)
5. 행렬 3×3 — 3분배 (각 행·열에 세 종류가 정확히 한 번씩)
6. 행렬 3×3 — 크기 진행
7. 행렬 3×3 — 복합 (회전 + 개수)
8. 수열 — 등차 / 등비 / 피보나치 / 교대 / 제곱
9. 공간 — 전개도 접기
10. 도형 — 대칭·반전

각 생성기는 `generate(seed) → { question, explanation }`를 반환한다. 오답 선택지도 규칙을 의도적으로 어긋나게 해서 만든다(예: 회전 각도만 틀림, 개수만 틀림) — 그래야 매력적인 오답이 되고 "왜 틀렸는지" 설명도 자동으로 나온다.

**난이도**는 규칙의 개수와 변형 폭으로 조절한다. 1(단일 규칙) / 2(규칙 2개 결합) / 3(규칙 2개 + 노이즈).

**IQ 20문항 구성:** 생성 12문항(난이도 1-2-3 분포) + 수기 언어유추 8문항. 언어유추는 의미 관계라 생성이 부자연스러워 직접 쓴다.

### 4.3 문항 풀 규모 (v1 목표)

| 카테고리 | 출제 | 풀 | 배수 |
|---|---|---|---|
| IQ 도형/수열 | 12 | 무한(생성) | — |
| IQ 언어유추 | 8 | 40 | 5.0× |
| 성격 16유형 | 24 (축당 6) | 60 (축당 15) | 2.5× |
| MZ | 15 | 50 | 3.3× |
| 사투리 (지역당) | 12 | 30 | 2.5× |
| 심리 | 12 × 3종 | 고정 | — |

수기 작성 총계 ≈ **366문항 + 해설** (언어유추 40 + 성격 60 + MZ 50 + 사투리 180 + 심리 36).

심리 테스트는 축 균형이 깨지면 결과가 무의미해지므로 **랜덤 출제하지 않고 12문항 고정**으로 운용한다. 대신 테스트를 3종 제공해 다양성을 확보한다.

### 4.4 출제 (assemble)

```
assemble(testId, seed, options) → Question[]
```

- 시드 기반 셔플로 풀에서 뽑는다
- **난이도 분포를 강제한다** (예: 사투리 12문항 = 쉬움 4 / 보통 5 / 어려움 3)
- 유형형은 **축별 문항 수를 강제한다** (축당 정확히 6문항)
- 직전 회차에 나온 문항을 우선 배제한다(최근 사용 ID를 저장해 다음 회차에서 후순위)
- 풀이 부족하면 크래시 대신 중복을 허용하고 경고를 남긴다

### 4.5 채점

**정답형:** 정답률 → 급수(9급 최하 ~ 1급 최상). 기본 매핑은 아래와 같고, 카테고리별로 `content/grades.json`에서 구간을 조정한다.

| 정답률 | 급수 |
|---|---|
| 100% | 1급 |
| 90~99% | 2급 |
| 80~89% | 3급 |
| 70~79% | 4급 |
| 60~69% | 5급 |
| 50~59% | 6급 |
| 40~49% | 7급 |
| 25~39% | 8급 |
| 0~24% | 9급 |

각 급수에는 카테고리별 코믹한 칭호가 붙는다 (예: 사투리 경상도 1급 = "부산 이모 인정", 9급 = "서울 사람 확정"). 칭호는 `grades.json`에 함께 정의한다.

IQ는 급수와 함께 추정 점수를 표시하되, "오락용 추정치"임을 반드시 병기한다. 추정 점수는 정답률을 평균 100 · 표준편차 15 구간에 선형 대응시킨 값이며(하한 70 · 상한 145), 규준 표본에 근거한 값이 아니라는 사실을 결과 화면에 명시한다.

**유형형은 두 가지 채점 방식으로 나뉜다.**

*(a) 축 방식 — 성격 16유형 고사*

축별 가중치 합계의 부호로 4글자 코드를 결정한다.

- 선택지 가중치는 `-2 | -1 | +1 | +2` 4단계이며 **중립(0)을 두지 않는다**
- 그럼에도 축당 6문항이면 합계 0(동점)이 나올 수 있다. **동점 시 해당 축의 마지막 응답 방향으로 결정**하고, 결과 화면에 "이 축은 거의 반반입니다"를 표시한다
- 각 축의 치우침 정도(%)를 결과 카드에 막대로 표시한다

*(b) 득표 방식 — 심리 테스트 3종*

각 선택지가 특정 유형에 1표를 던지고, 최다 득표 유형이 결과가 된다.

- 심리 테스트 1종당 **유형 5개**, 문항 12개, 문항마다 선택지 4개(서로 다른 유형에 투표)
- 동점 시 **더 뒤쪽 문항에서 득표한 유형**을 우선한다 (뒤쪽 문항일수록 변별력 높은 문항을 배치)
- 축 방식과 득표 방식은 `typeScore.ts` 안의 별도 함수로 구현하고 각각 유닛 테스트를 붙인다

두 방식 모두 결과 화면에서 문항별로 "이 문항이 어느 축/유형을 쟀고 당신의 응답이 어떻게 기여했는가"를 열람할 수 있다.

## 7. 에러 처리

**최우선: 잘못된 문항이 앱에 들어가지 못하게 한다.** 오답 해설이 나가면 스토어 별점 1점 리뷰가 된다.

`tools/validate-content.ts`가 커밋 전과 CI에서 실행되며 다음을 검사한다.

- `answerIndex`가 `choices` 범위 안에 있는가
- 정답형 문항에 `explanation`이 비어 있지 않은가
- 문항 ID 중복이 없는가
- 유형형 문항의 `axis`가 유효하고, 축별 문항 수가 출제 요구치 이상인가
- 심리 테스트에서 5개 유형의 전체 득표 기회가 균등한가 (유형 간 차이 ±1 이내) — 한 유형만 나오기 쉬운 편향 방지
- 선택지 개수가 규격대로인가 (텍스트 문항 4개 / IQ 도형·수열 5개)
- 선택지 텍스트 중복(같은 문항 안에 동일한 선택지 2개)이 없는가
- 급수 테이블 구간이 0~만점을 빈틈없이 덮는가
- 각 생성기가 만든 표본 100개에서 정답이 유일한가 (오답 4개가 정답 스펙과 모두 다른가)

**런타임 폴백:**

| 상황 | 처리 |
|---|---|
| 풀 부족으로 출제 수 미달 | 중복 허용해 채우고 콘솔 경고 (크래시 금지) |
| AsyncStorage 읽기/쓰기 실패 | 메모리 상태로 계속 진행, 기록만 유실, 사용자에게 조용히 토스트 |
| 결과 카드 캡처 실패 | 텍스트 공유로 폴백 |
| 딥링크 파싱 실패 | 홈으로 이동 (에러 화면 없음) |
| 생성기 예외 | 해당 문항을 수기 풀에서 대체 |

## 8. 테스트 전략

**엔진 (핵심, 커버리지 우선):**

- 생성기 10종 각각에 대한 속성 테스트 — 시드 1000개를 돌려 (a) 정답이 항상 유일한가 (b) 해설 문자열이 비어 있지 않은가 (c) 선택지가 정확히 5개인가
- 시드 재현성 — 같은 시드는 항상 같은 문항을 만든다
- 채점 경계값 — 만점 / 0점 / 각 급수 경계 정확히 위아래
- 유형 채점 — 축 동점 시 "마지막 응답 방향" 규칙이 지켜지는가, 16개 코드가 모두 도달 가능한가
- 출제 — 난이도 분포 강제, 축별 문항 수 강제, 최근 문항 배제

**콘텐츠:** `validate-content.ts`를 Jest에서도 실행해 데이터가 깨지면 테스트가 빨간불이 되게 한다.

**UI (스모크 수준):** 각 화면이 크래시 없이 렌더되는가, 문항 선택 → 다음 문항 진행, 결과 화면 도달, 오답노트 항목 생성. 픽셀 검증은 하지 않는다.

### 9.1 개발 환경 준비

- 서명키를 새로 생성하고 `C:\workAndroid\_서명키_백업` 관례에 따라 백업한다
- Android 릴리스는 **로컬 `./gradlew bundleRelease`** 로 빌드한다 (무료·빠름). EAS는 iOS 빌드용으로 남긴다

### 9.3 Play 스토어 제출 체크리스트

- 데이터 안전: 수집 없음 / 공유 없음
- 광고 포함: 아니오
- 콘텐츠 등급: 전체 이용가

- 스토어 설명에 **수익 관련 문구를 쓰지 않는다** ("광고 없음", "무료", "인앱결제 없음" 금지 — 추후 광고 도입 시 설명을 고쳐야 하는 상황을 피한다). 단 데이터 안전 신고는 사실대로 한다

- 폰트·아이콘을 전부 번들한다
- 공유는 시스템 공유시트만 사용한다
- Android 전용 API(Toast 등)를 직접 쓰지 않고 크로스 플랫폼 래퍼를 둔다

## 10. 구현 순서

문항 366개 작성이 이 프로젝트에서 가장 무거운 작업이므로, **엔진과 화면을 먼저 완성해 적은 문항으로 앱 전체가 돌아가는 상태를 만든 뒤 문항을 채운다.** 문항을 먼저 쓰면 스키마가 바뀔 때마다 전부 손봐야 한다.

1. **뼈대** — Expo 프로젝트 생성, prebuild, 권한 제거 확인, 로컬 릴리스 빌드가 폰에 올라가는 것까지
2. **디자인 시스템** — 토큰, Button/Card/Badge/Certificate, 폰트 번들
3. **엔진** — 타입, 시드 RNG, 출제, 정답형 채점, 유형형 채점 2종, 급수 테이블 (전부 유닛 테스트 동반)
4. **IQ 생성기** — 규칙 10종 + SvgFigure 렌더러 + 정답 유일성 속성 테스트
5. **화면** — 홈 → 문항 → 결과 → 해설, 각 카테고리 10문항 정도의 최소 데이터로 연결
6. **저장·공유** — 기록, 오답노트, 결과 카드 캡처·공유, 딥링크 도전장
7. **문항 채우기** — 카테고리별로 나눠서 작성 + 검증 스크립트 통과
8. **출시 준비** — 서명키, AAB, 개인정보처리방침, 스토어 등록 자료, 실기기 검증(Android 8 포함)
