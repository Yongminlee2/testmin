# IQ 도형 문제 총량 확대 Implementation Plan

**Goal:** 도형 생성기의 서로 다른 퍼즐을 36개 → 79개로 늘려, 즉시 재응시할 때 반복되는 문항을 20개 중 9.5개에서 4개 수준으로 줄인다.

**Architecture:** 새 생성기를 만들지 않는다. 기존 다섯 생성기의 **파라미터 공간을 넓히는 것만** 한다. 규칙 자체는 그대로이므로 사용자가 배워야 할 것이 늘지 않고, 이미 실기기에서 검증된 동작이 바뀌지 않는다.

**전제:** 이 계획은 `docs/plans/2026-08-07-testmin-iq.md`(계획 3) 완료 후에 시작한다. 356 테스트 통과 상태.

## Global Constraints

계획 3에서 이어지는 제약. 전부 그대로 유효하다.

- TypeScript strict + `noUncheckedIndexedAccess`, `tsc --noEmit` 클린
- `src/engine/**`는 순수 TypeScript — React·RN·파일시스템 import 금지
- 결정적: 같은 시드는 항상 같은 문항. `Math.random()` 금지
- 사용자 노출 문구는 한국어, 파일은 UTF-8
- **한글 파일에 PowerShell 텍스트 치환 금지** (PowerShell 5.1이 UTF-8을 깨뜨린다)
- 5지선다, 정답 정확히 하나
- `__tests__/engine/iq/generators.test.ts` 수정 금지

### 이 계획에서 절대 깨뜨리면 안 되는 것

기존 테스트가 이미 전부 지키고 있다. **넓히다가 하나라도 빨간불이 되면 그건 설계가 틀린 것이지 테스트가 낡은 게 아니다.**

| 규칙 | 왜 |
|---|---|
| ★ 예측 대조 | 정답 오표시를 잡는 유일한 테스트 |
| 회전은 삼각형에만 | 원·마름모·정사각형은 90° 배수에서 자기 자신이라 **픽셀 단위로 같은 오답**이 생긴다 |
| 크기 3단계 간격 ≥ 0.12 | 기계는 0.01 차이도 "다른 도형"으로 보지만 사람은 못 본다 |
| 점이 겹치지 않음 | 겹치면 화면의 개수와 정답이 어긋나 **맞게 센 사람이 틀렸다고 나온다** |
| 해설이 격자와 일치 | 이 앱의 핵심 약속 |
| 오답 구성이 규칙 위반별로 하나씩 | 무작위로 뽑으면 가장 교육적인 오답이 빠진다 |
| 문항 안에서 `filled` 일관 | 부분 불일치는 `filled`를 뜻하지 않은 구분 기준으로 만든다 |
| 용량 > 수요 (엄격히 큼) | `validate:content`가 검사. 넓히면 여유가 늘어날 뿐이라 통과해야 정상 |

## Task 1 — `rotation` 9 → 24, `count` 6 → 13

**Files:**
- Modify: `src/engine/iq/generators/rotation.ts`, `src/engine/iq/generators/count.ts`
- Test: 기존 `rotation.test.ts`, `count.test.ts`에 추가

### `rotation.ts` — 시작 각도를 8가지로

현재 `start`가 `STEPS`(90·180·270)에서 뽑혀 **0°가 아예 안 나온다.** 시작 각도를 45° 배수 8가지로 넓힌다.

```ts
const STEPS = [90, 180, 270] as const;          // 그대로
const STARTS = [0, 45, 90, 135, 180, 225, 270, 315] as const;   // 신규
```

`start = STARTS[pickInt(rand, 0, STARTS.length - 1)]`. 3 × 8 = **24가지.**

- 오답은 지금처럼 `answerRotation + 90/180/270`과 `+45`. 45는 90·180·270과 mod 360에서 절대 겹치지 않으므로 다섯 개가 항상 서로 다르다.
- 삼각형은 45° 간격 8방향이 전부 눈으로 구분된다. **회전을 쓰는 생성기는 계속 삼각형만.**
- 해설의 `첫 칸이 ${start}°이므로`가 45·135° 같은 값도 자연스럽게 읽힌다.

**추가 테스트:**
```ts
  test('시드 500개에서 시작 각도 8가지가 모두 나온다', () => {
    // 격자 첫 칸의 rotation을 모아 Set 크기가 8인지. 0°가 빠져 있던 게 원래 결함이다.
  });
  test('서로 다른 퍼즐이 24가지다', () => {
    // (첫 칸 각도, 두 번째 칸과의 차이)로 퍼즐을 식별해 Set 크기 확인
  });
```

### `count.ts` — 배치표 12칸 + 방향·보폭 확장

**배치표를 3×4 격자로 바꾼다.** 흩어진 배치보다 줄 맞춘 배치가 **세기 쉽다** — 개수를 묻는 문제에서 그게 더 낫다.

```ts
/**
 * 왼쪽 위부터 행 우선으로 채운다. x 간격 0.28, y 간격 0.21·0.22·0.21.
 * 최소 중심간 거리 0.21 > 점 지름 0.16이므로 어느 조합도 겹치지 않는다.
 * (지름을 0.18에서 0.16으로 줄였다 — 12칸을 넣으면서 간격이 0.228에서 0.21로 좁아졌다.)
 */
const DOT_POSITIONS: ReadonlyArray<readonly [number, number]> = [
  [0.22, 0.18], [0.5, 0.18], [0.78, 0.18],
  [0.22, 0.39], [0.5, 0.39], [0.78, 0.39],
  [0.22, 0.61], [0.5, 0.61], [0.78, 0.61],
  [0.22, 0.82], [0.5, 0.82], [0.78, 0.82],
];
const DOT_SIZE = 0.16;
```

**파라미터 조합 13가지.** 각 조합의 상한은 "모든 칸과 모든 선택지가 1~12에 들어갈 것"에서 역산했다. 오답이 `answer ± 1, ± 2`이므로 `answer ≥ 3`이고 `answer + 2 ≤ 12`여야 한다.

| 방향 | 보폭 | `start` 범위 | 칸 개수식 | 정답 | 가짓수 |
|---|---|---|---|---|---|
| 증가 | 1 | 1~3 | `start + (r+c)` | `start+4` = 5~7 | 3 |
| 증가 | 2 | 1~2 | `start + 2(r+c)` | `start+8` = 9~10 | 2 |
| 감소 | 1 | 7~12 | `start - (r+c)` | `start-4` = 3~8 | 6 |
| 감소 | 2 | 11~12 | `start - 2(r+c)` | `start-8` = 3~4 | 2 |

합 **13가지.**

> **각 범위의 하한·상한이 전부 load-bearing이다. 주석으로 이유를 남길 것.**
> 감소·보폭2의 `start ≥ 11`은 `answer - 2 ≥ 1`(점 0개짜리 선택지 금지) 때문이고,
> 증가·보폭2의 `start ≤ 2`는 `answer + 2 ≤ 12`(배치표 길이) 때문이다.
> 누가 "정리"하면 점 0개짜리 선택지나 배열 범위 초과가 나온다.

해설은 보폭도 말해야 한다: `점이 ${step}개씩 늘어납니다` / `${step}개씩 줄어듭니다`.

**추가 테스트:**
```ts
  test('시드 500개에서 보폭 1과 2가 모두 나온다', () => { /* 첫 두 칸 차이의 절댓값 */ });
  test('서로 다른 퍼즐이 13가지다', () => { /* (첫 칸 개수, 두 번째 칸과의 차이) */ });
```
기존 테스트는 전부 그대로 통과해야 한다 — 특히 겹침 검사와 `모든 선택지의 점 개수가 1개 이상`.

## Task 2 — `fill`·`size`·`distribute` 축 교환으로 각각 2배

세 생성기가 같은 형태의 확장을 받는다: **어느 축이 어느 속성을 맡는지 뒤집는다.** 규칙은 그대로고 문제만 새로워진다.

**Files:** `src/engine/iq/generators/{fill,size,distribute}.ts` + 각 테스트

### `fill.ts` 6 → 12

현재 열=종류, 행=채움 고정. `swapped` 파라미터를 추가해 뒤집는다(행=종류, 열=채움).
`kindOffset`(3) × `startFilled`(2) × `swapped`(2) = **12.**

**해설이 실제 축을 말해야 한다.** 지금 문구는 `열마다 도형이 …, 행마다 색이 …`로 고정돼 있다. 뒤집힌 경우 `행마다 도형이 …, 열마다 색이 …`가 되어야 한다.
→ 해설 값은 **이미 채운 `cells`에서 읽는다**(계획 3에서 확정한 규칙). 축 이름도 `swapped`에서 직접 만들지 말고, 격자를 보고 "같은 줄에서 종류가 일정한 방향"을 찾아 쓰는 편이 어긋날 여지가 없다.

### `size.ts` 6 → 12

현재 행=종류, 열=크기. `swapped`로 뒤집는다(열=종류, 행=크기).
`kindOffset`(3) × `ascending`(2) × `swapped`(2) = **12.**

`SIZES = [0.3, 0.5, 0.7]`은 **그대로 둔다.** 간격 0.2는 화면 구분 최소치 0.12의 1.6배이고, 여기를 건드리면 계획 3에서 실기기로 확인한 것이 무효가 된다.

### `distribute.ts` 9 → 18

현재 종류가 `(r + c)`, 크기가 `(r + 2c)` 라틴 방진. `swapped`로 두 공식을 맞바꾼다.
`kindOffset`(3) × `sizeOffset`(3) × `swapped`(2) = **18.**

두 방진이 서로 직교하는 성질은 맞바꿔도 유지된다 — **그래도 기존 직교성 테스트가 계속 통과하는지 확인할 것.** 그 테스트는 이 규칙의 핵심이고, 계획 3에서 내가 쓴 검사가 부족해 구현자가 잡아낸 자리다.

**세 생성기 공통 추가 테스트:**
```ts
  test('시드 500개에서 축 배치 두 가지가 모두 나온다', () => { /* 격자에서 역산 */ });
  test('서로 다른 퍼즐이 N가지다', () => { /* 12 / 12 / 18 */ });
  test('해설이 격자의 실제 축을 말한다', () => {
    // 뒤집힌 문항의 해설이 "행마다 도형"이라 하는데 격자는 열이 종류를 정하고 있으면 실패
  });
```
