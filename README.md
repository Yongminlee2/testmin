# 테스트의 민족

IQ · 성격 16유형 · MZ · 사투리 · 심리 테스트를 한 앱에서 보는 한국어 퀴즈 앱.

**모든 문항이 정답과 "왜 그것이 답인가"를 함께 갖는다.** 이 앱의 출발점이자 다른 퀴즈 앱과 갈라지는 지점이다. 사투리 문항은 사람이 근거와 함께 작성했고, IQ 도형 문항은 규칙에서 문제·정답·해설이 동시에 생성된다.

- 패키지명: `com.testmin.app`
- 지원: Android 8(API 24) ~ 최신(API 36). iOS는 이후 대응
- 네트워크 없이 전부 오프라인 동작
- **사용자 노출 권한 0개**

### Windows 빌드 주의 — 경로에 한글이 있으면 실패한다

이 프로젝트에서 가장 오래 붙잡았던 문제다. 자세한 내용은 [docs/build-notes.md](docs/build-notes.md).

`TEMP` / `TMP` 환경변수에 한글이 들어 있으면 네이티브 빌드가 깨진다. AGP가 `prefab_command.bat`을 UTF-8로 쓰는데 `cmd.exe`는 시스템 코드페이지로 읽는다. 한글 한 글자가 3바이트 대 2바이트로 어긋나면서 **이어지는 줄의 앞 글자가 잘려 나간다.** 오류 메시지는 전혀 다른 것을 가리키고, 줄바꿈 문자(LF/CRLF) 문제로 오진하기 딱 좋다.

```bash
export TEMP=/c/workAndroid/tmp-ascii
export TMP=/c/workAndroid/tmp-ascii
```

Gradle 홈도 ASCII 경로여야 한다. 단, `*-ascii`라는 이름의 정션(junction)이 한글 홈을 가리키고 있으면 아무 소용이 없다 — 실제 디렉터리인지 확인할 것.

## 핵심 설계 결정

### 1. IQ 문항은 저장하지 않고 생성한다

도형 문항을 JSON으로 쌓으면 수백 개를 손으로 그려야 하고, 해설도 따로 써야 하고, 둘이 어긋나도 알 수 없다.

대신 **규칙을 코드로 갖는 생성기**를 만들었다. 같은 규칙에서 문제·정답·해설이 **동시에** 나오므로 셋이 어긋날 수 없다.

| 생성기 | 규칙 | 난이도 | 서로 다른 퍼즐 |
|---|---|---|---|
| `rotation` | 삼각형이 일정 각도씩 회전 | 1 | 9 |
| `count` | 오른쪽·아래로 갈수록 점이 늘거나 준다 | 1 | 6 |
| `fill` | 열이 종류를, 행이 채움을 정한다 | 2 | 6 |
| `size` | 행이 종류를, 열이 크기를 정한다 | 2 | 6 |
| `sequence` | 등차·등비·피보나치·교대·제곱 수열 | 2 | 1,000+ |
| `distribute` | 그레코-라틴 방진 (종류·크기가 직교) | 3 | 9 |

도형은 `FigureSpec`이라는 선언적 데이터로 표현하고 `SvgFigure`가 따로 그린다. **생성기는 그림 그리는 법을 모른다.**

> **알려진 한계 — 도형 문제 총량이 아직 적다.** 위 표의 도형 생성기 다섯 종을 합쳐도 서로 다른 퍼즐이 **36개**뿐인데, 한 세트는 도형 문항을 18개 쓴다. 그래서 **바로 다시 응시하면 20문항 중 평균 9.5개가 이미 본 문제**다. 시드 구조나 중복 방지 로직의 결함이 아니라 규칙당 파라미터 공간이 좁아서 생기는 총량 문제이고, 생성기를 늘리거나 각 규칙의 파라미터 범위를 넓혀야 해결된다. 수열 생성기는 1,000가지가 넘으므로 여기 해당하지 않는다.

### 2. 같은 시드는 항상 같은 문제를 만든다

`mulberry32` 시드 난수를 쓴다. 덕분에 오답노트가 문항 전체가 아니라 `(생성기 id, 시드)` 두 값만 저장하고 나중에 문항을 복원할 수 있다.

### 3. 선택지는 출제 시점에 섞는다

문항 데이터에서 정답이 몇 번인지는 의미가 없다. `assemble()`이 시드로 순서를 섞고 `answerIndex`를 따라 옮긴다. **단, 성격 문항은 섞지 않는다** — 리커트 척도라 선택지 순서 자체가 뜻을 갖는다. 이 구분은 "`answerIndex`가 숫자인 문항만 섞는다"는 조건으로 **엔진 층(`assemble.ts`·`assembleTyped.ts`)에서는** 구조에 박아뒀다.

이 보장은 엔진 층에서 끝난다. IQ는 `assemble()`을 거치지 않고 생성기가 자기 rng로 직접 섞으며, 렌더 층(`QuizRunner`)에는 타입 수준의 구조적 보장이 없다 — 셔플/비셔플 분리를 지키는 것은 "QuizRunner가 세션에 담긴 선택지 순서를 그대로 렌더한다"는 회귀 테스트(`QuizRunner.order.test.tsx`)뿐이다.

### 4. 상표 회피

"MBTI"라는 표기를 코드·화면·문서 어디에도 쓰지 않는다. 16유형 별명도 전부 자체 창작이며, 널리 알려진 유형 명칭을 쓰지 않는다는 것을 테스트가 강제한다.

### 5. 추정 점수에는 안내 문구가 따라붙는다

IQ 추정 점수는 정답률을 70~145 구간에 선형 대응시킨 값이다. **규준 표본이 없으므로 실제 지능검사가 아니다.**

이 문구를 상수로 두고 화면이 import해서 쓰게 하면, 새 화면(공유 카드, 오답노트 헤더)이 빼먹어도 아무것도 실패하지 않는다. 그래서 **채점 결과 타입의 필수 필드**로 만들었다. 점수를 꺼내면 문구가 같이 손에 들어온다.

### 6. 권한 0개

Config Plugin이 매니페스트 병합 단계에서 `INTERNET`, `SYSTEM_ALERT_WINDOW`, `VIBRATE`, 저장소 권한을 제거한다. 릴리스 APK에 남는 것은 `androidx.core`가 넣는 signature 수준 권한 하나뿐이며, `aapt2 dump permissions`로 매 릴리스마다 확인한다.

## 테스트

### 방법론 — "이 규칙을 어긴 코드를 만들면 테스트가 빨간불이 되는가"

이 프로젝트에서 반복해서 나온 결함은 **틀린 코드가 아니라, 맞는 코드를 지켜주지 않는 테스트**였다.

계기가 된 사건이 있다. 개발 초기에 **96개 테스트 통과 + 타입 검사 클린 + 릴리스 APK 빌드 성공 + 권한 감사 통과** 상태로 **모든 문제의 정답이 1번인 앱**이 만들어졌다. 15문항 전부 `answerIndex: 0`인데 선택지를 섞는 코드가 어디에도 없었다. 태스크별 코드 리뷰 13번이 전부 놓쳤다.

이후 모든 규칙에 대해 **일부러 망가뜨린 변형(뮤테이션)을 만들어 돌려보고**, 테스트가 실제로 빨간불이 되는지 확인한 뒤에야 통과시킨다. 초록불로 남으면 그 규칙은 지켜지고 있지 않은 것이다.

이 방식으로 잡은 것들:

| 어긴 규칙 | 초록불로 남았던 테스트 | 결과 |
|---|---|---|
| 축 `percent` 0나눗셈 가드 삭제 | 10개 전부 통과 | 결과 화면 막대에 `NaN` |
| 압승 시 동점 플래그 리셋 삭제 | 6개 전부 통과 | 3대1 압승인데 "거의 반반" 표시 |
| 축 부족 시 타축 보충 금지 삭제 | 9개 전부 통과 | 성격 결과가 무의미해짐 |
| 점 좌표표의 한 항목 중복 | 7개 전부 통과 | 두 점이 겹쳐 그려져 개수가 어긋남 |
| 해설을 무관한 문장으로 교체 | 7개 전부 통과 | 해설이 규칙을 설명하지 않음 |
| 레지스트리에서 생성기 삭제 | 241개 전부 통과 | 생성기가 조용히 출제에서 빠짐 |
| 격자 전체를 한 종류로 | 12개 전부 통과 | "행이 종류를 정한다"는 전제 소멸 |
| 라틴 방진의 직교성 파괴 | 10개 전부 통과 | 문제가 퇴화해 크기를 볼 필요가 없어짐 |

각 항목은 그 자리에서 테스트를 추가해 막았다.

### 생성기가 반드시 갖추는 테스트 네 종류

1. **예측 대조** — 그려진 격자에서 규칙을 **역산해** 정답을 독립적으로 계산하고, 생성기가 표시한 것과 대조한다. 생성기 내부 변수를 다시 읽으면 동어반복이라 의미가 없다.
2. **시각적 유효성** — 도형이 겹치지 않는가, 크기 차이가 화면에서 구분되는가, 숫자가 버튼을 넘치지 않는가.
3. **해설 내용** — 해설이 격자에서 역산한 값을 실제로 말하는가. "비어 있지 않다"는 검사는 아무것도 지키지 않는다.
4. **레지스트리 등록** — 디스크에서 생성기 모듈을 **발견**해 등록 여부를 확인한다. 목록을 손으로 유지하면 "잊어버리면 조용히 통과"라는 원래 문제가 그대로 돌아온다.

### 기계가 원리상 못 잡는 것

자동 검사는 **스펙 차이만** 알고 **보이는 차이**는 모른다. 다음은 시드 수천 개를 돌려도 절대 안 잡히므로 실기기에서 사람이 확인한다.

- **원은 아무리 돌려도 똑같이 보인다.** 마름모는 90°가 자기 자신, 정사각형도 90° 배수는 구분 불가. 회전을 구분 기준으로 쓰는 생성기를 **삼각형 전용**으로 제한한 이유다.
- **크기 차이 0.01도 기계는 "다른 도형"으로 본다.** 그래서 크기 단계를 0.3 / 0.5 / 0.7 세 개로 고정했다. 9칸을 단조 증가시키면 한 단계가 0.075가 되어 화면에서 구분되지 않는다.
- **도형 선택지에는 글자가 없다.** 접근성 이름을 안 붙이면 스크린리더에서 버튼 다섯 개가 전부 무명이 된다.
- **해설이 말이 되는가**는 사람만 안다.

## 개발 일지

### 1단계 — 기반 + 사투리 고사

프로젝트 뼈대, 네이티브 빌드 파이프라인, 시드 난수, 채점·급수 엔진, 디자인 시스템, 경상도 사투리 15문항, 화면 4종.

**네이티브 빌드가 며칠 막혔다.** 원인이 세 겹이었다. Gradle 홈으로 쓰던 `*-ascii` 디렉터리가 실은 한글 홈을 가리키는 정션이었고, `compileSdk 37`에는 정수 플랫폼이 없었으며(`android-37.0`만 존재), 진짜 원인은 위에 적은 `%TEMP%` 한글 경로 문제였다. 줄바꿈 문자 문제라는 오진을 두 번 거친 뒤, 3줄짜리 LF 파일·472바이트 LF 파일·역슬래시 두 배 파일 세 가지를 만들어 전부 정상 실행되는 것을 보이고서야 배제할 수 있었다.

**출시 직전까지 갔던 결함**은 위 "테스트" 절에 적은 정답 위치 문제다. 전체 브랜치 리뷰에서야 발견됐다. 근본 원인이 하나 더 있었다 — 문항 작성 지시서에 *"정답이 전부 0번인 건 의도다, 앱이 표시할 때 섞는다"* 라고 **존재하지 않는 기능을 사실처럼 적어놓아서**, 이상하다고 느낀 작업자의 정당한 의심을 막았다.

### 2단계 — 유형형 시험 (성격 · 심리)

정답이 없는 시험을 위한 두 번째 채점 방식. 축 합계형(4개 축 × 6문항 → 4글자 코드)과 최다 득표형(12문항 → 5유형 중 1개).

**정/역 문항 균형**이 이 단계의 핵심이었다. 모든 문항이 같은 방향이면 "매우 그렇다"만 고르는 사람이 네 축 전부 한쪽 극단으로 몰린다. 그건 성격이 아니라 순응 성향을 재는 것이다. 실기기에서 24번 연속 "매우 그렇다"를 눌러 확인했다.

축 합계가 0이 되는 동점 처리, 무응답 축의 0나눗셈, 압승인데 "반반"이라 표시되는 플래그 리셋 — 세 가지 모두 코드는 맞았지만 지켜주는 테스트가 없었고, 뮤테이션으로 하나씩 드러났다.

### 3단계 — IQ 고사 (진행 중)

도형 생성기 6종, 출제·채점·급수, 화면.

**계획서에 있던 오류를 작업 중에 네 번 잡았다.** 전부 "규칙은 맞는데 그것을 검사하는 방법이 틀린" 경우였다.

- 그레코-라틴 방진에서 **종류의 유일성과 크기의 유일성을 각각** 확인하는 것으로는 부족했다. 두 방진이 직교하지 않아도 그 검사는 통과한다. 9개 (종류, 크기) 조합이 전부 달라야 한다는 검사를 따로 넣었다.
- 수열의 교대 규칙 판정에 `stepA ≠ stepB` 조건이 빠져 있었다. **등차수열은 항상 교대수열이기도 하다** — 한 칸 건너뛴 항들이 공차가 두 배인 등차수열 두 개가 되기 때문이다. 500시드 중 97개가 이중 판정이었다.
- 감소 등차수열의 해설이 `"41 + -9 = 32"`를 출력했다. 음수 공차를 템플릿에 그대로 끼운 탓이다.
- 출제기의 생성기 순환이 난이도별 카운터가 아니라 전역 슬롯 인덱스를 썼다. 특정 생성기에 용량보다 많은 슬롯이 배정되어 **결정적으로 예외**가 났다.

**릴리스 게이트가 조합 제약을 못 보는 문제**도 여기서 나왔다. `validate:content`는 생성기를 낱개로만 검사하고 출제 설정을 통과시키지 않았다. 출제 설정을 세 가지로 바꿔보니 전부 300/300 시드에서 예외가 나는데 게이트는 **exit 0**으로 통과했다. 용량 대 수요 검사를 게이트에 추가했다.

같은 뿌리의 문제를 세 층에서 반복해 만난 셈이다: 태스크 사이(1단계), 테스트 사이(3단계 초반), 릴리스 게이트(3단계 후반). **단위를 각각 검사하는 것은 단위들의 조합을 검사하지 않는다.**

마지막으로 **실기기에서 20문항을 끝까지 풀어 결함 두 개를 더 찾았다.** 둘 다 테스트가 전부 초록불인 상태였다.

- 문항이 바뀌어도 스크롤이 맨 위로 돌아가지 않아, 아래쪽 선택지를 누르면 **다음 문항의 도형을 지나친 자리에 착지**했다. 글자 문항은 한 화면에 들어가서 여태 드러나지 않았고, 도형 문항이 되어서야 보였다.
- 결과 화면 버튼은 "틀린 15문항 해설 보기"인데 해설 화면은 20문항을 전부 보여줬다. 화면 쪽이 옳았다 — 문항마다 정답/오답 배지가 있으니 맞힌 것도 보여주는 게 설계 의도다. 문구가 틀린 것이었다.

한 판을 실제로 플레이하지 않았으면 둘 다 그대로 출시됐을 것이다.

## 실기기 검증

에뮬레이터가 아니라 실기기에서 확인한다. 빌드 성공과 테스트 통과는 "안 깨졌다"는 증거지 "동작한다"는 증거가 아니다.

| 기기 | Android |
|---|---|
| SM-G988N (S20 Ultra) | 13 (SDK 33) |
| SM-A165N (A16) | **16 (SDK 36)** |

매 단계 확인 항목:

- 시험을 **끝까지 한 판** 풀어본다
- 정답 위치가 한쪽으로 쏠리지 않는가 (1번을 12번 연속 눌러 확인)
- 도형이 제대로 그려지고, 선택지 다섯 개가 **화면에서** 서로 다른가
- 해설을 읽고 화면의 격자와 대조해 말이 되는가
- 추정 점수 옆에 안내 문구가 **같은 화면에** 보이는가
- **Android 15/16 edge-to-edge**: 상태바(시계·배터리)와 하단 내비게이션(뒤로가기)이 콘텐츠에 가려지지 않는가. 제스처 내비게이션과 3버튼 양쪽 모두
- 설치한 APK의 빌드 시각이 최신 커밋보다 나중인가 (수정 전 APK를 설치해놓고 "고쳐졌다"고 판단한 적이 있다)
