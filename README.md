# 테스트의 민족

IQ · MBTI식 16유형 · MZ · 사투리 · 맞춤법 · 순우리말 · 고사성어 · 심리 테스트를 한 앱에서 보는 한국어 퀴즈 앱.
**앱을 설치하지 않아도 웹에서 그대로 응시할 수 있다** — 같은 코드가 안드로이드와 웹 양쪽으로 나간다.

기획·콘텐츠 구성·앱 구현·검증·배포를 직접 진행하고 있는 개인 프로젝트다.

**모든 문항이 정답과 "왜 그것이 답인가"를 함께 갖는다.** 이 앱의 출발점이자 다른 퀴즈 앱과 갈라지는 지점이다. 텍스트 문항은 근거와 함께 직접 작성했고, IQ 도형 문항은 설계한 규칙에서 문제·정답·해설이 동시에 생성된다.

- 개발·운영: `Yongminlee2`
- 패키지명: `com.testmin.app`
- 지원: Android 7.0(API 24) ~ 최신(API 36). iOS는 이후 대응
- 웹: GitHub Pages 배포 (`npm run build:web`)
- 앱 안내·개인정보처리방침·이용 안내·지원: https://yongminlee2.github.io/legal/testmin/
- Android 앱은 네트워크 없이 전부 오프라인 동작
- **사용자 노출 권한 0개**

### Windows 빌드 주의 — 경로에 한글이 있으면 실패한다

이 프로젝트에서 가장 오래 붙잡았던 문제다. 자세한 내용은 [docs/build-notes.md](docs/build-notes.md).

`TEMP` / `TMP` 환경변수에 한글이 들어 있으면 네이티브 빌드가 깨진다. AGP가 `prefab_command.bat`을 UTF-8로 쓰는데 `cmd.exe`는 시스템 코드페이지로 읽는다. 한글 한 글자가 3바이트 대 2바이트로 어긋나면서 **이어지는 줄의 앞 글자가 잘려 나간다.** 오류 메시지는 전혀 다른 것을 가리키고, 줄바꿈 문자(LF/CRLF) 문제로 오진하기 딱 좋다.

```bash
export TEMP=/c/workAndroid/tmp-ascii
export TMP=/c/workAndroid/tmp-ascii
```

Gradle 홈도 ASCII 경로여야 한다. 단, `*-ascii`라는 이름의 정션(junction)이 한글 홈을 가리키고 있으면 아무 소용이 없다 — 실제 디렉터리인지 확인할 것.

## 핵심 설계 결정

### 1. IQ 문항은 저장하지 않고 생성한다

도형 문항을 JSON으로 쌓으면 수백 개를 손으로 그려야 하고, 해설도 따로 써야 하고, 둘이 어긋나도 알 수 없다.

대신 **규칙을 코드로 갖는 생성기**를 만들었다. 같은 규칙에서 문제·정답·해설이 **동시에** 나오므로 셋이 어긋날 수 없다.

| 생성기 | 규칙 | 난이도 | 서로 다른 퍼즐 |
|---|---|---|---|
| `rotation` | 삼각형이 일정 각도씩 회전 | 1 | 24 |
| `count` | 오른쪽·아래로 갈수록 점이 늘거나 준다 | 1 | 13 |
| `fill` | 한 축이 종류를, 다른 축이 채움을 정한다 | 2 | 12 |
| `size` | 한 축이 종류를, 다른 축이 크기를 정한다 | 2 | 12 |
| `sequence` | 등차·등비·피보나치·교대·제곱 수열 | 2 | 1,000+ |
| `distribute` | 그레코-라틴 방진 (종류·크기가 직교) | 3 | 18 |

도형은 `FigureSpec`이라는 선언적 데이터로 표현하고 `SvgFigure`가 따로 그린다. **생성기는 그림 그리는 법을 모른다.**

> **재응시 반복.** 도형 생성기 다섯 종을 합쳐 서로 다른 퍼즐이 **79개**이고 한 세트가 18개를 쓴다. 바로 다시 응시하면 20문항 중 평균 4개 정도가 겹친다(확대 전에는 9.5개였다). 더 줄이려면 규칙을 추가해야 한다.

### 2. 같은 시드는 항상 같은 문제를 만든다

`mulberry32` 시드 난수를 쓴다. 덕분에 오답노트가 문항 전체가 아니라 `(생성기 id, 시드)` 두 값만 저장하고 나중에 문항을 복원할 수 있다.

### 3. 선택지는 출제 시점에 섞는다

문항 데이터에서 정답이 몇 번인지는 의미가 없다. `assemble()`이 시드로 순서를 섞고 `answerIndex`를 따라 옮긴다. **단, 성격 문항은 섞지 않는다** — 리커트 척도라 선택지 순서 자체가 뜻을 갖는다. 이 구분은 "`answerIndex`가 숫자인 문항만 섞는다"는 조건으로 **엔진 층(`assemble.ts`·`assembleTyped.ts`)에서는** 구조에 박아뒀다.

이 보장은 엔진 층에서 끝난다. IQ는 `assemble()`을 거치지 않고 생성기가 자기 rng로 직접 섞으며, 렌더 층(`QuizRunner`)에는 타입 수준의 구조적 보장이 없다 — 셔플/비셔플 분리를 지키는 것은 "QuizRunner가 세션에 담긴 선택지 순서를 그대로 렌더한다"는 회귀 테스트(`QuizRunner.order.test.tsx`)뿐이다.

### 4. MBTI식 16유형 표기와 자체 콘텐츠

사용자가 시험 성격을 바로 이해하도록 화면에는 `MBTI식 16유형 고사`라고 표시한다.
다만 공식 MBTI 검사가 아닌 오락용 자체 문항임을 인트로와 결과 안내에서 분명히 밝힌다.
16유형의 별명·설명·궁합 문구는 모두 자체 창작이며, 널리 알려진 상용 유형 명칭을
복제하지 않는다는 것을 테스트가 강제한다. 결과에는 E/I·S/N·T/F·J/P 양쪽 비율을
함께 표시해 네 글자만 단정적으로 보여주지 않는다.

### 5. 추정 점수에는 안내 문구가 따라붙는다

IQ 추정 점수는 정답률을 70~145 구간에 선형 대응시킨 값이다. **규준 표본이 없으므로 실제 지능검사가 아니다.**

이 문구를 상수로 두고 화면이 import해서 쓰게 하면, 새 화면(공유 카드, 오답노트 헤더)이 빼먹어도 아무것도 실패하지 않는다. 그래서 **채점 결과 타입의 필수 필드**로 만들었다. 점수를 꺼내면 문구가 같이 손에 들어온다.

### 6. 권한 0개

Config Plugin이 매니페스트 병합 단계에서 `INTERNET`, `SYSTEM_ALERT_WINDOW`, `VIBRATE`, 저장소 권한을 제거한다. 릴리스 APK에 남는 것은 `androidx.core`가 넣는 signature 수준 권한 하나뿐이며, `aapt2 dump permissions`로 매 릴리스마다 확인한다.

## 테스트

### 방법론 — "이 규칙을 어긴 코드를 만들면 테스트가 빨간불이 되는가"

이 프로젝트에서 반복해서 나온 결함은 **틀린 코드가 아니라, 맞는 코드를 지켜주지 않는 테스트**였다.

계기가 된 사건이 있다. 개발 초기에 **96개 테스트 통과 + 타입 검사 클린 + 릴리스 APK 빌드 성공 + 권한 감사 통과** 상태로 **모든 문제의 정답이 1번인 앱**이 만들어졌다. 15문항 전부 `answerIndex: 0`인데 선택지를 섞는 코드가 어디에도 없었다. 태스크별 코드 리뷰 13번이 전부 놓쳤다.

이후 모든 규칙에 대해 **일부러 망가뜨린 변형(뮤테이션)을 만들어 돌려보고**, 테스트가 실제로 빨간불이 되는지 확인한 뒤에야 통과시킨다. 초록불로 남으면 그 규칙은 지켜지고 있지 않은 것이다.

이 방식으로 잡은 것들:

| 어긴 규칙 | 초록불로 남았던 테스트 | 결과 |
|---|---|---|
| 축 `percent` 0나눗셈 가드 삭제 | 10개 전부 통과 | 결과 화면 막대에 `NaN` |
| 압승 시 동점 플래그 리셋 삭제 | 6개 전부 통과 | 3대1 압승인데 "거의 반반" 표시 |
| 축 부족 시 타축 보충 금지 삭제 | 9개 전부 통과 | 성격 결과가 무의미해짐 |
| 점 좌표표의 한 항목 중복 | 7개 전부 통과 | 두 점이 겹쳐 그려져 개수가 어긋남 |
| 해설을 무관한 문장으로 교체 | 7개 전부 통과 | 해설이 규칙을 설명하지 않음 |
| 레지스트리에서 생성기 삭제 | 241개 전부 통과 | 생성기가 조용히 출제에서 빠짐 |
| 격자 전체를 한 종류로 | 12개 전부 통과 | "행이 종류를 정한다"는 전제 소멸 |
| 라틴 방진의 직교성 파괴 | 10개 전부 통과 | 문제가 퇴화해 크기를 볼 필요가 없어짐 |

각 항목은 그 자리에서 테스트를 추가해 막았다.

### 생성기가 반드시 갖추는 테스트 네 종류

1. **예측 대조** — 그려진 격자에서 규칙을 **역산해** 정답을 독립적으로 계산하고, 생성기가 표시한 것과 대조한다. 생성기 내부 변수를 다시 읽으면 동어반복이라 의미가 없다.
2. **시각적 유효성** — 도형이 겹치지 않는가, 크기 차이가 화면에서 구분되는가, 숫자가 버튼을 넘치지 않는가.
3. **해설 내용** — 해설이 격자에서 역산한 값을 실제로 말하는가. "비어 있지 않다"는 검사는 아무것도 지키지 않는다.
4. **레지스트리 등록** — 디스크에서 생성기 모듈을 **발견**해 등록 여부를 확인한다. 목록을 손으로 유지하면 "잊어버리면 조용히 통과"라는 원래 문제가 그대로 돌아온다.

### 기계가 원리상 못 잡는 것

자동 검사는 **스펙 차이만** 알고 **보이는 차이**는 모른다. 다음은 시드 수천 개를 돌려도 절대 안 잡히므로 실기기에서 사람이 확인한다.

- **원은 아무리 돌려도 똑같이 보인다.** 마름모는 90°가 자기 자신, 정사각형도 90° 배수는 구분 불가. 회전을 구분 기준으로 쓰는 생성기를 **삼각형 전용**으로 제한한 이유다.
- **크기 차이 0.01도 기계는 "다른 도형"으로 본다.** 그래서 크기 단계를 0.3 / 0.5 / 0.7 세 개로 고정했다. 9칸을 단조 증가시키면 한 단계가 0.075가 되어 화면에서 구분되지 않는다.
- **도형 선택지에는 글자가 없다.** 접근성 이름을 안 붙이면 스크린리더에서 버튼 다섯 개가 전부 무명이 된다.
- **해설이 말이 되는가**는 사람만 안다.

## 개발 일지

아래에는 설계·구현 과정에서 직접 결정한 내용, 실제 기기와 웹에서 발견한 문제,
문제를 재현하고 검증한 과정을 단계별로 기록했다.

### 1단계 — 기반 + 사투리 고사

프로젝트 뼈대, 네이티브 빌드 파이프라인, 시드 난수, 채점·급수 엔진, 디자인 시스템, 경상도 사투리 15문항, 화면 4종.

**네이티브 빌드가 며칠 막혔다.** 원인이 세 겹이었다. Gradle 홈으로 쓰던 `*-ascii` 디렉터리가 실은 한글 홈을 가리키는 정션이었고, `compileSdk 37`에는 정수 플랫폼이 없었으며(`android-37.0`만 존재), 진짜 원인은 위에 적은 `%TEMP%` 한글 경로 문제였다. 줄바꿈 문자 문제라는 오진을 두 번 거친 뒤, 3줄짜리 LF 파일·472바이트 LF 파일·역슬래시 두 배 파일 세 가지를 만들어 전부 정상 실행되는 것을 보이고서야 배제할 수 있었다.

**출시 직전까지 갔던 결함**은 위 "테스트" 절에 적은 정답 위치 문제다. 전체 브랜치 리뷰에서야 발견됐다. 근본 원인이 하나 더 있었다 — 문항 작성 지시서에 *"정답이 전부 0번인 건 의도다, 앱이 표시할 때 섞는다"* 라고 **존재하지 않는 기능을 사실처럼 적어놓아서**, 이상하다고 느낀 작업자의 정당한 의심을 막았다.

### 2단계 — 유형형 시험 (성격 · 심리)

정답이 없는 시험을 위한 두 번째 채점 방식. 축 합계형(4개 축 × 6문항 → 4글자 코드)과 최다 득표형(12문항 → 5유형 중 1개).

**정/역 문항 균형**이 이 단계의 핵심이었다. 모든 문항이 같은 방향이면 "매우 그렇다"만 고르는 사람이 네 축 전부 한쪽 극단으로 몰린다. 그건 성격이 아니라 순응 성향을 재는 것이다. 실기기에서 24번 연속 "매우 그렇다"를 눌러 확인했다.

축 합계가 0이 되는 동점 처리, 무응답 축의 0나눗셈, 압승인데 "반반"이라 표시되는 플래그 리셋 — 세 가지 모두 코드는 맞았지만 지켜주는 테스트가 없었고, 뮤테이션으로 하나씩 드러났다.

### 3단계 — IQ 고사

도형 생성기 6종, 출제·채점·급수, 화면.

**계획서에 있던 오류를 작업 중에 네 번 잡았다.** 전부 "규칙은 맞는데 그것을 검사하는 방법이 틀린" 경우였다.

- 그레코-라틴 방진에서 **종류의 유일성과 크기의 유일성을 각각** 확인하는 것으로는 부족했다. 두 방진이 직교하지 않아도 그 검사는 통과한다. 9개 (종류, 크기) 조합이 전부 달라야 한다는 검사를 따로 넣었다.
- 수열의 교대 규칙 판정에 `stepA ≠ stepB` 조건이 빠져 있었다. **등차수열은 항상 교대수열이기도 하다** — 한 칸 건너뛴 항들이 공차가 두 배인 등차수열 두 개가 되기 때문이다. 500시드 중 97개가 이중 판정이었다.
- 감소 등차수열의 해설이 `"41 + -9 = 32"`를 출력했다. 음수 공차를 템플릿에 그대로 끼운 탓이다.
- 출제기의 생성기 순환이 난이도별 카운터가 아니라 전역 슬롯 인덱스를 썼다. 특정 생성기에 용량보다 많은 슬롯이 배정되어 **결정적으로 예외**가 났다.

**릴리스 게이트가 조합 제약을 못 보는 문제**도 여기서 나왔다. `validate:content`는 생성기를 낱개로만 검사하고 출제 설정을 통과시키지 않았다. 출제 설정을 세 가지로 바꿔보니 전부 300/300 시드에서 예외가 나는데 게이트는 **exit 0**으로 통과했다. 용량 대 수요 검사를 게이트에 추가했다.

같은 뿌리의 문제를 세 층에서 반복해 만난 셈이다: 태스크 사이(1단계), 테스트 사이(3단계 초반), 릴리스 게이트(3단계 후반). **단위를 각각 검사하는 것은 단위들의 조합을 검사하지 않는다.**

마지막으로 **실기기에서 20문항을 끝까지 풀어 결함 두 개를 더 찾았다.** 둘 다 테스트가 전부 초록불인 상태였다.

- 문항이 바뀌어도 스크롤이 맨 위로 돌아가지 않아, 아래쪽 선택지를 누르면 **다음 문항의 도형을 지나친 자리에 착지**했다. 글자 문항은 한 화면에 들어가서 여태 드러나지 않았고, 도형 문항이 되어서야 보였다.
- 결과 화면 버튼은 "틀린 15문항 해설 보기"인데 해설 화면은 20문항을 전부 보여줬다. 화면 쪽이 옳았다 — 문항마다 정답/오답 배지가 있으니 맞힌 것도 보여주는 게 설계 의도다. 문구가 틀린 것이었다.

한 판을 실제로 플레이하지 않았으면 둘 다 그대로 출시됐을 것이다.

### 4단계 — 기록·오답노트, 그리고 콘텐츠 채우기

성적표·오답노트 탭, 앱 아이콘, MZ 고사 15문항, 사투리 5개 지역 75문항.

**오답노트는 문항을 저장하지 않는다.** `(생성기 id, 시드)`나 문항 id만 남기고, 볼 때 다시 만들어 낸다. 3단계에서 만들어 둔 왕복 계약이 여기서 값을 했다. 복원 못 하는 항목은 목록에서 조용히 빠진다 — 빈 줄을 남기지 않는다.

저장 데이터는 계산과 위험의 결이 다르다. 그래서 검사도 "깨진 데이터를 넣어도 앱이 안 죽는가", "항목 하나가 망가져도 나머지가 살아남는가", "같은 문항이 쌓이지 않는가"로 짰다.

**안드로이드 자동 백업을 껐다.** 기본값이 켜짐이라 응시 기록이 구글 서버로 올라가는데, 이 앱은 인터넷 권한을 아예 제거하고 오프라인 동작을 표방한다. 표방하는 것과 실제가 어긋나면 안 된다.

**앱 아이콘이 아예 없었다.** `app.json`에 `icon`도 `splash`도 없어서 그동안 Expo 기본 아이콘으로 빌드되고 있었고, `assets/`에는 템플릿 잔재만 있었다. 디자인 시스템을 따라 직접 그렸다.

**콘텐츠는 사람이 판단할 몫이라 직접 썼다.** 신조어는 지식이 낡을 위험이 실재하므로 이번 달 유행어를 피하고 몇 해에 걸쳐 자리 잡은 말만 골랐다. 서울·경기는 표준어가 곧 서울말이라 다른 지역과 같은 방식이 성립하지 않아, 표준어인 줄 알았던 것과 사라진 옛 서울말을 묻는 형태로 바꿨다.

검증기와 테스트가 두 번 제 일을 했다 — 충청 문항의 정답이 47% 한쪽에 쏠린 것, 그리고 지역·카테고리가 열리면서 "콘텐츠 없는 곳은 잠겨 있다"는 전제가 깨진 것을 각각 잡아냈다.

### 5단계 — 난이도 상향, 고사 확장, 그리고 웹

IQ가 쉽다는 지적에서 시작했다. 기존 생성기 여섯은 전부 "한 속성이 일정하게 변한다"는 형태라
규칙 하나만 찾으면 풀렸다. 규칙을 **두 번 읽어야** 풀리는 세 종을 더했다.

| 생성기 | 읽어야 하는 것 |
|---|---|
| `logic` | 한 줄의 앞 두 칸을 겹쳐 세 번째 칸이 나온다 (xor·and·or 중 무엇인지도 알아내야 한다) |
| `sum` | 가로 한 줄의 점 개수 합이 모든 줄에서 같다 |
| `hardsequence` | 계차가 등차 / ×k 후 +c / 곱하는 수가 커짐 / 두 연산이 번갈아 |

출제 배분도 `{1:7, 2:7, 3:6}`에서 `{1:4, 2:7, 3:9}`로 옮겼다.

**"어렵게 만들었다"는 말을 테스트가 지키게 했다.** `hardsequence`에는 나온 수열이
등차나 등비인지 판정하는 함수를 두고, 하나라도 걸리면 실패시킨다. 그런데 이 판정이
언제나 거짓을 주는 껍데기여도 테스트는 초록불이다 — 그래서 같은 판정을 **난이도 2
생성기에 걸어 실제로 걸려 나오는지** 확인하는 대조 테스트를 나란히 뒀다.

**아이큐가 몇인지 크게 보여달라**는 요청은 그대로 따르되, 숫자만 크게 띄우면 실제 검사
점수로 읽힌다. 그래서 같은 카드 안에 70~145 눈금 위 위치와 "정답률 N%를 이 구간에 그대로
대응시킨 값"이라는 산출 근거를 함께 넣었다. 규준 표본이 없으므로 백분위는 쓰지 않는다.
기존 안내 문구는 그대로 함께 나간다.

**고사 세 종(맞춤법·순우리말·고사성어)을 추가하면서 화면을 복사하지 않았다.**
`app/test/g/[testId]/` 한 벌이 `SCORED_TESTS` 표를 읽고 동작한다. 홈 카드도 같은 표에서
파생시켰다 — 표 두 개가 어긋날 여지 자체를 없앤다. 새 고사는 **문항 JSON + 표 한 줄**이면 끝난다.
배선이 실제로 다 붙었는지(풀·급수표·홈 카드·경로)는 등록된 고사를 전부 도는 테스트가 지킨다.

콘텐츠 검증기가 또 한 번 제 일을 했다. 맞춤법 15문항의 정답이 1번에 67% 쏠린 것을 커밋 전에 잡아냈다.

**폰트 자막이 잘려 한자가 안 나올 뻔했다.** 시작 속도를 줄이려고 번들 폰트를
18.6MB → 9.03MB로 줄였는데, 그 서브셋에 고사성어의 한자가 없었다. 이건 화면을 열어보기
전에는 안 보이는 종류의 결함이라, `validate:content`에 **번들 폰트의 cmap을 직접 읽어
콘텐츠의 모든 글자가 들어 있는지** 확인하는 검사를 넣었다. 없는 글자가 있으면 릴리스가 막힌다.

마지막으로 **웹**이다. 자세한 내용은 아래 "웹" 절에 적었다. 요약하면, 정적 내보내기가
성공하는 것과 배포본이 도는 것은 별개였고, 브라우저에서 실제로 한 판씩 돌려보며
`baseUrl`·`.nojekyll`·동적 경로·`Alert` 무동작·공유 시트 부재를 하나씩 잡았다.

### 6단계 — 실제 배포, 그리고 궁합을 심리 테스트로

Pages 설정을 켠 뒤에도 두 번 더 막혔다. 첫 배포는 설정 전이라 당연히 실패했고,
설정을 켠 다음번엔 에러 메시지가 바뀌었다 —
`Branch "main" is not allowed to deploy to github-pages due to environment protection rules.`
`github-pages` 환경은 기본값으로 **저장소 기본 브랜치에서만** 배포를 허용하는데,
이 저장소는 아직 `feat/foundation`이 기본 브랜치였다. `main`에 워크플로를 걸어놓고
정작 배포는 기본 브랜치 조건에 막힌 것이다. 두 브랜치 모두에서 돌게 임시로 넓혀
일단 배포를 통과시켰다 — 기본 브랜치를 `main`으로 바꾸면 정리할 항목으로 남겨둔다.

CI 로그의 "Node.js 20 is deprecated" 경고도 살펴봤다. `actions/checkout`·`setup-node`·
`upload-pages-artifact`를 최신 메이저로 올리면 없어지는 경고이지만, 실제로 올려보기
전에 `upload-pages-artifact`의 action.yml을 버전별로 비교했다. v4부터 `include-hidden-files`
입력이 추가됐고 **기본값이 false**다 — 즉 그냥 올리면 `.nojekyll`(점으로 시작하는 파일)이
아티팩트에서 조용히 빠지고, 배포 전 단계에서 잡아둔 "Jekyll이 `_expo/`를 삼킨다"는 결함이
그대로 되살아난다. 눈에 보이는 경고 하나를 지우려다 이미 고친 결함을 새 코드로 재도입할
뻔했다. 경고는 무해하므로 액션 버전은 그대로 두기로 했다 — 이건 이 세션에서 실행하지
않은 변경이지만, 왜 안 했는지를 남겨두는 게 다음에 같은 유혹에 다시 안 낚이는 방법이다.

**궁합 카드(CompatCard)는 성격 16유형에만 있었다.** 컴포넌트 자체는 처음부터 범용으로
설계돼 있었는데("성격은 ENFP, 심리는 유형 이름" — 코드 주석에 이미 적혀 있었다) 배선이
안 돼 있었다. 문제는 성격의 16유형은 4글자를 하나씩 뒤집는 대칭 규칙이 있었지만, 심리
테스트 3종(연애·스트레스·소통)은 각각 5유형뿐이라 그 규칙을 못 쓴다는 점이었다 — 5는
홀수라 "서로가 서로를 가리키는" 대칭 짝짓기 자체가 수학적으로 불가능하다(홀수 크기
집합의 대합엔 항상 고정점이 남는다). 대신 유형 설명을 놓고 "표현 방식이 가까운 정도"라는
축을 하나 세우고, 오각형으로 배치해 이웃 두 개(잘 맞음)·정반대 방향 하나(부딪힘)를
골랐다 — 대칭은 아니지만 각 링크마다 왜 그런지 문장으로 밝히니 "근거 없이 단정하지
않는다"는 원칙은 그대로 지켜진다.

이 궁합 데이터를 검증하는 자동 검사가 이전엔 **하나도 없었다.** 지난 세션에 성격
16유형 궁합을 만들 때 "자기 자신을 안 가리키는지, 존재하지 않는 코드를 안 가리키는지"를
손으로 한 번 확인하고 끝났던 것이다. 이번에 4벌(성격 + 심리 3종)을 한 표로 묶어 검사하는
테스트를 추가하면서, 성격 데이터도 같이 자동 검사 대상이 됐다 — 손으로 확인하고 잊는
방식은 다음에 코드 하나만 바꿔도 조용히 깨질 수 있었다.

**S20 Ultra로 실기기에서 5단계 작업분을 전부 확인했다.** IQ 20문항을 끝까지 풀어
결과 화면에서 "IQ 78"이 70~145 눈금과 근거 문구("정답률 10%를…")와 함께 뜨는 것,
새 생성기(`sum`의 주사위 눈 배치·`hardsequence`의 곱수 증가 수열)가 실제로 화면에
나오는 것, 맞춤법·순우리말·고사성어 세 고사를 각각 완주해 결과·해설·성적표까지
확인했다. 고사성어는 특히 문제·선택지·해설·근거 네 자리 전부에서 한자(錦上添花 등)가
깨지지 않는 것까지 봤다 — 어제 폰트 서브셋을 줄이며 생긴 위험이 실제로는 없다는
증거다. 이 과정에서 **인트로 화면의 안내 문구가 낡아 있었다.** "회전·개수·채움·분배·
크기·수열, 여섯 가지 유형"이라고 여전히 6종 시절 문구를 달고 있었는데 실제로는 이미
9종이었다 — 코드는 고쳤지만 화면에 박아 둔 설명 문장은 안 건드린 전형적인 누락이다.
자동 테스트는 이런 종류의 결함을 못 잡는다. 문구를 8종("…겹침·합, 여덟 가지 유형")으로
고치고 실기기에서 다시 확인했다.

### 7단계 — 결과별 코믹 140장과 코믹 관찰일지

처음에는 결과 이미지가 58개라서 충분해 보였다. 하지만 **파일 개수와 결과 조합 개수는
다른 문제**였다. MBTI 16개와 심리 30개는 각각 고유했지만, MZ·사투리·맞춤법·순우리말·
고사성어는 같은 급수 그림 9개를 공유했다. “테스트별 × 결과별로 겹치지 않는다”는 기준으로
세면 정답형 고사만 5 × 9 = 45장이 필요했다. 여기서 한 번 더 엄격하게 보니 사투리는
경상도·전라도·충청도·강원도·제주도·서울·경기의 6개 지역이 각기 다른 문항을 쓰는
별도 변형이었다. 지역이 다른데 같은 9장을 보여주는 것도 사용자 입장에서는 중복이다.

그래서 사투리를 `6지역 × 9급 = 54장`으로 완전히 분리하고 결과 자산을 **총 140장**으로
다시 구성했다.

| 결과군 | 계산 | 그림 수 |
|---|---:|---:|
| 성격 16유형 | 16유형 | 16 |
| 심리 테스트 | 6테스트 × 5유형 | 30 |
| 일반 정답형 고사 | 4테스트 × 9급 | 36 |
| 사투리 고사 | 6지역 × 9급 | 54 |
| IQ | 4동물 퍼즐 구간 | 4 |

그림만 다르고 전부 같은 화풍이면 테스트가 바뀌었다는 느낌이 약하다. 그래서 성격은
현대 에디토리얼 코믹, 연애는 파스텔 구아슈, 스트레스는 신문 스크린프린트, 소통은
팝아트, 충전은 펠트 스톱모션, 미루기는 노트 낙서, 여행은 빈티지 포스터, IQ는 클레이,
MZ는 Y2K 픽셀, 맞춤법은 신문 펜화, 순우리말은 수채 그림책,
고사성어는 수묵 목판화로 분리했다. 같은 앱의 굵은 카드 틀 안에서 **재료감과 장면 문법은
테스트마다 다르게** 보이도록 한 것이다.

사투리 안에서도 지역끼리 겹치지 않는다. 경상도는 까치 민화, 전라도는 판소리 민화,
충청도는 도자기 디오라마, 강원도는 산악 리노컷, 제주도는 현무암 종이 콜라주,
서울·경기는 레트로 도시 웹툰 콜라주를 썼다. 결과 급수가 같아도 캐릭터·배경·재료감이
모두 다르다.

결과 설명도 한두 문장으로 끝내지 않는다. 그림 아래에 `평소 장면`·`숨은 장점`·`다음 한 수`
세 칸의 **코믹 관찰일지**를 붙였다. 약점을 단정하거나 사람을 낮추지 않고, 먼저 습관을
우스운 생활 장면으로 보여준 다음 그 안의 장점을 짚고 마지막에 작은 선택 하나만 제안한다.
카드 끝에는 “웃자고 만든 관찰일지이며 사람은 상황에 따라 달라진다”는 문구도 항상 붙는다.

이 기준은 사람의 기억에 맡기지 않았다. `resultIllustrations.test.ts`가 코드 안의 WebP
`require` 경로를 직접 뽑아 **140개인지, 중복이 0개인지** 검사하고, 파일 내용의 SHA-256
해시도 비교한다. 캡션과 세 줄 관찰일지도 결과마다 고유한지 확인하므로 새 결과를 하나
추가하고 그림이나 설명을 돌려 쓰면 테스트가 즉시 실패한다.

### 8단계 — 결과 템플릿을 시험의 의미에 맞게 분리

그림과 문장이 고유해도 **결과를 보여주는 순서와 항목 이름이 시험에 맞지 않으면** 억지로
끼워 넣은 인상이 남는다. 실제 배포본을 360×800 화면에서 다시 풀어보니 심리 테스트의
결과명이 긴 그림 뒤에 있었고, 스트레스 결과에도 성격 유형용 `이런 사람과 잘 맞아요`와
`사람 사이가 네 글자로 정해지지는 않습니다`가 남아 있었다. 정답형 고사는 시험 종류와
상관없는 기차·커피 장면을 공용으로 조합해 문맥과 조사까지 어색해지는 경우가 있었다.

결과 계층을 시험군별로 나눴다. 성격은 `유형·별명·설명·축`을 먼저, 심리는
`반응 이름·설명·선택 근거`를 먼저, 정답형 고사는 `급수·제목·정답 수`를 먼저 보여준다.
그 아래 기록 카드도 성격은 `캐릭터 사용 설명서`, 스트레스는 `스트레스 대피 매뉴얼`,
맞춤법은 `교정실 리포트`처럼 시험마다 제목·세부 항목·주의 문구를 별도로 둔다. 심리 유형
조합 카드도 연애·스트레스·소통·충전·미루기·여행에 맞는 제목으로 각각 분리했다.

IQ는 중복되던 점수·인증서 카드를 하나로 합치고, 인간 IQ 숫자를 동물에게 붙이는 대신
문어·라쿤·까마귀류·침팬지의 알려진 인지 강점을 빌린 네 가지 코믹 비유를 넣었다. 화면에는
사람과 동물의 IQ를 수치로 비교할 수 없다는 안내를 함께 표시한다. 결과 문구·급수 제목에는
`찍기의 장인`처럼 낮은 점수를 사람의 정체성으로 단정하는 표현을 없애고, 현재 학습 단계와
다음 행동을 가볍게 설명하는 문장으로 바꿨다.

이 점검은 `resultPresentation.test.ts`에 고정했다. 테스트별 기록 템플릿의 고유성,
스트레스 등 심리 결과에 MBTI 문구가 섞이지 않는지, 정답형 장면이 해당 시험 어휘와
맞는지, 낮은 급수에 비하성 제목이 없는지, IQ 동물 구간 네 개가 모두 연결되는지를 검사한다.
변경 후 성격·스트레스·맞춤법·IQ를 다시 완주했고 360px에서 가로 넘침이 없음을 확인했다.

### 9단계 — 작은 Android 화면의 하단 메뉴와 IQ 도형 보기 정리

하단 메뉴를 단순히 화면 아래에 띄우면 제조사·내비게이션 방식에 따라 시스템 버튼과 붙어
보였다. 탭 바 바깥에 크림색 안전 영역을 두고, 보고된 하단 inset 뒤에도 8dp 간격을
추가했다. inset을 0으로 잘못 주는 구형 기기는 최소 12dp를 보장한다. 네 메뉴는 연필·트로피·
펼친 책·톱니바퀴 아이콘으로 구분하고 선택된 메뉴만 노란 배경을 유지했다.

IQ 도형 오지선다는 공용 카드의 검은 그림자 레이어가 열 전체로 늘어나고, 다섯 번째 보기가
2열 아래에 혼자 남는 문제가 있었다. 도형 보기 전용 크기 계산을 추가해 5개는 3개+2개로
가운데 정렬하고, 320px 화면에서는 도형까지 함께 줄어들게 했다. 각 보기는 동일한 클릭 영역과
`1번 보기`부터 `5번 보기`까지의 접근성 이름을 유지한다. 320px·412px 화면과 Android 릴리스
빌드에서 확인했다.

웹에서는 1900px가 넘는 화면 폭을 카드 계산에 그대로 사용해 도형은 작고 선택지만 화면 끝까지
늘어나는 문제가 남아 있었다. 시험 본문은 최대 920px, 도형 보기 카드는 3열 기준 최대 200px로
제한하고 문제 도형과 보기 도형만 넓은 화면에서 한 단계 키웠다. 1902×698과 320×700을 함께
확인했다.

같은 넓은 화면에서 하단 메뉴는 모바일용 10px 라벨과 18px 아이콘을 그대로 사용해 읽기
어려웠다. 768px 이상에서는 라벨 13px, 아이콘 24px, 메뉴 높이 72px로 키우고 전체 폭은
760px로 제한했다. 웹이 자동으로 라벨을 아이콘 옆에 놓아 말줄임표가 생기지 않도록 위치도
아이콘 아래로 고정했다. 1884px와 360px에서 비교했다.

결과 코믹은 앱과 웹에서 모두 카드 폭 100%를 사용해 1800px대 웹 화면에서 그림 하나가 화면을
가득 채웠다. Android·iOS 앱은 기존 크기를 유지하고 웹에서만 일러스트와 관찰일지 묶음을 최대
560px로 제한했다. 1861px에서는 결과 제목과 그림 전체가 첫 화면에 함께 들어오고, 360px 모바일
웹에서는 기존처럼 가로폭을 채우는 것을 확인했다. 전체 테스트는 558개로 늘었다.

| 기기 | Android |
|---|---|
| SM-G988N (S20 Ultra) | 13 (SDK 33) |
| SM-A165N (A16) | **16 (SDK 36)** |

매 단계 확인 항목:

- 시험을 **끝까지 한 판** 풀어본다
- 정답 위치가 한쪽으로 쏠리지 않는가 (1번을 12번 연속 눌러 확인)

- 추정 점수 옆에 안내 문구가 **같은 화면에** 보이는가
- **Android 15/16 edge-to-edge**: 상태바(시계·배터리)와 하단 내비게이션(뒤로가기)이 콘텐츠에 가려지지 않는가. 제스처 내비게이션과 3버튼 양쪽 모두
- 설치한 APK의 빌드 시각이 최신 커밋보다 나중인가 (수정 전 APK를 설치해놓고 "고쳐졌다"고 판단한 적이 있다)

## 웹 (GitHub Pages)

같은 코드가 안드로이드 앱과 웹 양쪽으로 나간다. 화면·엔진·콘텐츠를 하나도 따로 두지 않았다 —
`expo export --platform web`이 Expo Router의 파일 기반 라우트를 그대로 정적 HTML로 뽑는다.

```bash
npm run build:web    # dist/ 생성
npm run serve:web    # 배포본과 같은 방식으로 로컬 확인
```

`main`에 올리면 `.github/workflows/deploy-web.yml`이 타입 검사 → 콘텐츠 검증 → 테스트를 모두
통과한 뒤에만 배포한다. 저장소 Settings → Pages → Source를 **GitHub Actions**로 한 번 바꿔둬야 한다.

### 웹으로 옮기며 실제로 걸린 것들

정적 내보내기가 성공했다고 배포본이 도는 건 아니었다. 브라우저에서 한 판씩 돌려보며 잡은 것들이다.

**`baseUrl`이 없으면 빈 화면이 된다.** GitHub Pages는 `https://<계정>.github.io/testmin/` 아래로
서빙하는데, 번들 경로가 루트(`/_expo/...`)로 나가면 전부 404가 난다. `app.json`의
`experiments.baseUrl`을 `/testmin`으로 맞춰야 한다.

**`.nojekyll`이 없으면 번들이 통째로 사라진다.** Pages는 Jekyll을 거치고, Jekyll은 밑줄로
시작하는 폴더를 무시한다. expo는 번들을 `_expo/`에 넣는다. 워크플로에서 이 빈 파일을 만든다.

**동적 경로는 `generateStaticParams` 없이는 링크가 안 열린다.** `app/test/g/[testId]/`가
`[testId]` 자리 그대로 내보내져서, 앱 안에서 눌러 들어가면 되는데 주소를 직접 열거나
새로고침하면 404가 났다. 네 화면 모두에 등록한 고사 목록을 돌려주는 함수를 달아 실제 페이지로 만든다.

**react-native-web의 `Alert`는 아무 일도 하지 않는다.** 개발 콘솔에만 찍힌다. "준비 중입니다"
안내가 웹에서 통째로 사라지는 건 사소하지만, 성적표의 **기록 삭제 확인창이 안 뜨는 건 다르다** —
버튼이 눌리기만 하고 아무 일도 안 일어나는 상태가 된다. `src/ui/dialog.ts`로 감싸
웹에서는 브라우저 대화상자를 쓰고, 그 분기를 테스트로 못 박았다.

**웹에는 공유 시트가 없다.** `expo-sharing`은 웹에서 `isAvailableAsync()`가 거짓이라 캡처만
하고 조용히 끝났다. 캡처 자체는 되므로 그 결과를 브라우저 다운로드로 넘기고 버튼 이름도
"결과 이미지 저장"으로 바꿨다.

**`<title>`을 껍데기에 쓰면 무시된다.** 정적 렌더러가 helmet용 빈 `<title>`을 먼저 넣기 때문에,
`app/+html.tsx`에 하나 더 쓰면 브라우저가 앞의 빈 것을 골라 탭 이름이 URL로 뜬다.
제목은 화면마다 `expo-router/head`로 채운다(`src/ui/PageTitle.tsx`).

**로컬 확인 서버가 배포본과 달랐다.** 파이썬 기본 `http.server`는 `/foo` 요청에 `foo.html`을
주지 않는다. 그래서 로컬에서만 "Unmatched Route"가 떴다. `tools/serve-web.py`가 Pages와 같은
규칙(확장자 보정 + `/testmin` 접두사)으로 서빙한다.

### 10단계 — 앱·웹 전체 GUI 점검과 넓은 화면 정리

웹은 1440×900 데스크톱과 360×800 모바일 화면에서 홈, 안내, IQ 도형 문항, 결과, 성적표,
오답노트, 설정을 차례로 확인했다. Android는 SM-A165N 실기기에 최신 릴리스 APK를 설치해
홈, IQ 안내·문항, 성적표, 오답노트, 설정과 하단 메뉴의 안전 영역을 다시 확인했다.

데스크톱에서 카드와 버튼이 화면 끝까지 늘어나던 문제는 앱 본문을 최대 920px로 제한해 해결했다.
하단 메뉴는 별도의 760px 프레임 안에 두어 넓은 화면에서도 중앙에 모이게 했고, 바깥 배경도
크림색으로 통일했다. 키보드 포커스 표시는 없애지 않고 둥근 검은 테두리로 바꿔 디자인과
접근성을 함께 유지했다. 모바일과 Android에서는 기존 100% 폭 계산을 그대로 사용한다.

IQ 오답노트는 접힌 항목의 문구가 비슷해 서로 구분하기 어려웠다. 도형 문제에는 56px 미리보기를
붙여 목록만 봐도 어떤 문제였는지 알 수 있게 했고, 펼치면 미리보기 대신 기존의 큰 문제 도형,
선택 답, 정답, 해설이 나온다. 콘텐츠 검증 254문항·생성형 1,800건·IQ 출제 2,000건과 전체
558개 테스트, 타입 검사, 웹 정적 내보내기, Android 릴리스 빌드를 모두 통과했다.

### 11단계 — 짧은 Android 화면의 IQ 도형 선택지 보정

앱과 웹의 17개 고사 흐름을 데스크톱·모바일 화면에서 다시 완주하고, Android는 일반 화면과
360×640dp 소형 화면을 나눠 확인했다. 일반 화면에서는 정상적이던 IQ 도형 오지선다의 두 번째
줄이 짧은 화면에서 시스템 제스처 영역에 닿는 문제를 발견했다.

화면 높이가 720dp보다 작을 때만 문제 도형을 220dp에서 180dp로, 보기 도형을 최대 80dp에서
60dp로 줄였다. 카드 폭과 97dp 이상의 세로 터치 영역은 유지해 누르기 편한 크기를 지켰다.
360×640dp에서는 마지막 보기 하단과 제스처 막대 사이에 51px 여백을 확보했고, 일반 화면과
넓은 웹 화면의 기존 배율은 그대로 유지했다. 이 높이별 계산은 단위 테스트로 고정했다.

### 12단계 — 공유 결과의 관계 지도와 설명 문구 정리

결과 이미지에 잘 맞는 유형과 박자를 맞춰볼 유형의 일러스트를 넣었지만, 처음에는 세 장을 한
줄에 나눠 담아 좁은 Android 화면에서 이미지와 글이 서로 자리를 빼앗았다. 관계 지도는 세로형
행으로 다시 만들고 각 그림을 72dp로 고정했다. 그림 프레임과 바깥 카드에는 넘침 방지를 넣고,
긴 유형명과 별명은 남은 폭 안에서 줄바꿈하도록 했다. 웹에서는 결과 일러스트와 같은 560px를
최대 폭으로 사용해 넓은 화면에서도 카드와 그림이 과하게 늘어나지 않는다.

공유용 카드에는 `잘 맞는 유형` 두 개와 `박자를 맞춰볼 유형` 하나만 간단히 보여주고, 자세한
이유와 선정 기준은 아래 관계 설명 카드에 남겼다. 같은 안내를 두 번 반복하던 문장은 걷어냈다.
연애·스트레스·소통·충전·미루기·여행의 주의 문구도 판결문처럼 딱딱하지 않게 리듬 체크,
번역 난이도, 동행 금지 명단 같은 표현으로 다듬되 실제 관계를 단정하지 않는 선은 지켰다.

웹은 1440×900과 390×844에서 홈·IQ 도형·심리 결과를 직접 조작하고 캡처했다. Android는
SM-A165N 실기기에 ARM 릴리스 APK를 설치해 홈, IQ 도형 오지선다, 실제 선택 후 다음 문항 진행,
심리 테스트 12문항 완주, 결과 상단과 관계 지도까지 확인했다. 140개 결과 그림의 파일 해시와
캡션·관찰일지 고유성, 콘텐츠 254문항, 전체 566개 테스트, 타입 검사, 웹 정적 내보내기와
Android 릴리스 빌드를 모두 통과했다.

### 13단계 — 상용 출시 품질과 신뢰 화면

테스트 수를 무작정 늘리는 대신 사용자가 다시 열 이유와 안심하고 쓸 근거를 보강했다. 홈에는
날짜마다 바뀌는 `오늘의 한 판`과 응시 횟수·발견한 시험군 수를 넣었다. 추천은 로컬 날짜와
등록된 시험 목록만으로 결정되므로 서버나 계정이 필요 없고, 같은 날에는 화면을 다시 열어도
추천이 제멋대로 바뀌지 않는다.

설정 화면은 단순 버전 표기에서 신뢰·데이터 관리 화면으로 확장했다. 계정·광고·분석 도구가
없고 기록이 기기에만 남는다는 점, 현재 응시 기록과 오답노트 개수, 전체 삭제 버튼을 한곳에
모았다. 앱 소개·개인정보처리방침·이용 안내·지원·오픈소스 고지 링크도 연결했다. 공개 문서는
앱 저장소와 분리된 `legal/testmin` 경로에 두어 앱 저장소가 비공개로 바뀌어도 Play Store와
사용자가 계속 접근할 수 있게 했다.

상용 아이콘과 Play Store용 512px 아이콘, 1024×500 특집 그래픽, 웹 공유 미리보기,
실기기 스크린샷 6장을 새로 맞췄다. 예기치 않은 렌더 오류가 나면 빈 화면 대신 기록이
남아 있다는 안내와 다시 시도 버튼을 보여주는 오류 경계도 추가했다. 릴리스 빌드에는 R8 코드
축소와 리소스 축소를 켰고, 최종 APK의 사용자 권한이 0개인지 `aapt`로 다시 확인했다.

SM-A165N(Android 16)에 축소 적용 릴리스 APK를 실제 설치해 콜드 스타트, 홈, 설정,
외부 개인정보처리방침 열기, IQ 도형 오지선다, 20문항 완주, 결과 점수·동물 비유·코믹
일러스트, 펼침형 오답 해설을 확인했다. 콘텐츠 254문항·생성형 1,800건·IQ 출제 2,000건,
전체 571개 테스트, 타입 검사, Expo Doctor 20개 항목, 웹 정적 내보내기를 모두 통과했다.

### 14단계 — 성격 룰렛 아이콘과 Play·AdSense 출시 준비

앱의 첫인상이 실제 콘텐츠와 맞도록, 머리 위 룰렛에서 네 감정 캐릭터가 결과를 기다리는
3D 코믹 이미지를 최종 아이콘으로 정했다. 선택 원본은
`store/assets/icon-master-personality-wheel.png`에 보관하고 `tools/make-icons.py` 한 번으로
앱 아이콘, Android adaptive·monochrome 아이콘, 파비콘, PWA 아이콘, Play 512px 아이콘,
피처 그래픽과 공유 이미지를 모두 같은 원본에서 다시 만들도록 했다. 따라서 아이콘을
바꿀 때 서로 다른 세대의 그림이 앱·스토어·웹에 섞이지 않는다.

GitHub Pages의 홈 제목은 `테스트의 민족 | 코믹 심리테스트·IQ·MBTI식 16유형`으로
정리하고 manifest, apple-touch-icon, robots.txt, 정적 라우트 기반 sitemap을 추가했다.
AdSense 게시자 값은 저장소 변수로만 주입한다. 값이 없으면 광고 스크립트와 ads.txt가
생기지 않아 로컬 개발과 승인 전 배포에서는 광고 요청이 발생하지 않는다. 웹 광고가
켜질 때 필요한 쿠키·맞춤 광고·동의 관리 안내는 공개 개인정보처리방침의 웹 항목에
분리했고, Android 앱은 계속 광고 SDK와 인터넷 권한 없이 유지한다.

Play 제출용으로 EAS production 프로필(AAB), 최신 API 36 설정, 스토어 설명·데이터 보안
답변·아이콘·피처 그래픽을 한곳에 맞췄다. 기존 운영 업로드 키는 Git에서 제외한
`credentials.json`과 `testmin-upload.jks`로 연결했고 EAS production·preview 프로필은
로컬 자격 증명을 사용한다. Play Console 계정 입력, AdSense 게시자 ID와 CMP 활성화는
계정 소유자가 콘솔에서 완료해야 하므로 저장소에는 넣지 않는다.
전체 572개 테스트, 콘텐츠 검증, 타입 검사, Expo Doctor 20/20, 웹 정적 내보내기를 통과했고 새 아이콘이
Android legacy·round·adaptive 리소스로 생성되는 것을 확인했다. R8·리소스 축소가 적용된
운영 키로 서명한 release AAB도 생성했고, AAB 내부 인증서 SHA-256이 원본 업로드 키와
일치하며 JAR 서명 검증을 통과하는 것을 확인했다.

### 15단계 — 앱 아이콘 구도와 Pages 하단 메뉴 보정

최종 아이콘이 Android 런처에서 확대되어 얼굴과 위쪽 색종이가 잘려 보이던 문제를 정리했다.
원본을 7% 잘라내던 방식은 없애고, 네 모서리의 검은 배경만 노란색으로 채워 원래 구도를
온전히 보존했다. Adaptive Icon 전경은 핵심 그림이 중앙 64% 안전 영역에 들어오도록 줄여
Samsung 원형 마스크를 포함한 여러 런처 모양에서도 얼굴·룰렛·감정 캐릭터가 남게 했다.
같은 생성 스크립트로 앱 아이콘, 파비콘, PWA 아이콘, Play 아이콘, 피처 그래픽과 공유
미리보기도 다시 맞췄다.

GitHub Pages의 좁은 모바일 화면에서는 하단 메뉴 자체가 아니라 한글 라벨의 아래 획이
13px 줄 높이에 눌려 잘려 보였다. 웹의 768px 미만 화면에서만 메뉴 높이를 60px에서
64px로, 라벨 줄 높이를 13px에서 16px로, 항목 최소 높이를 50px에서 54px로 늘렸다.
Android는 같은 소스를 계속 사용하지만 `Platform.OS === 'web'` 분기 밖의 기존 수치를
그대로 사용하므로 앱 하단 메뉴에는 변화가 없다.

SM-A165N 앱 정보 화면에서 새 Adaptive Icon의 전체 구도를 확인했다. 웹은 320×568 로컬
배포본과 실제 GitHub Pages에서 하단 네 라벨의 아래 획과 12px 바닥 여백을 다시 확인했다.
관련 단위 테스트 8개, 타입 검사와 웹 정적 내보내기를 통과했으며, 이번 보정에서는 사용자의
요청에 따라 APK나 AAB를 새로 빌드하지 않았다.

### 16단계 — Google Play 제출 자료 최종 정리

Play Console에서 그대로 옮겨 적을 앱 이름, 설명, 카테고리, 연락처, 광고·접근·타겟층·
콘텐츠 등급·데이터 보안 답변과 신규 개인 계정의 비공개 테스트 절차를
`store/구글플레이-제출패키지.md`에 한 번에 정리했다. 개인정보처리방침, 지원, 약관,
앱 웹사이트가 모두 공개 상태로 HTTP 200을 반환하는 것도 다시 확인했다.

기존 1080×2340 캡처는 Play의 `긴 변이 짧은 변의 2배 이하` 필수 규격을 넘었기 때문에
원본은 보존하고 `store/assets/play-screenshots/`에 1080×2160, 24비트 PNG 제출본 6장을
따로 만들었다. 홈 화면은 현재 공개 버전의 `MBTI식 16유형 고사` 표기가 보이는 화면으로
갱신했고, 나머지는 실제 Android 캡처에서 상태 표시줄과 시스템 내비게이션 여백을 덜어냈다.

기존 릴리스 APK를 다시 검사해 패키지 `com.testmin.app`, 버전 코드 1, target API 36,
인터넷 권한 없음, RSA 2048비트 업로드 서명과 4개 ABI를 확인했다. 타입 검사, 콘텐츠
254문항·생성형 1,800건·IQ 출제 2,000건 검증, 68개 테스트 스위트의 573개 테스트와 웹
정적 내보내기를 모두 통과했다. 최종 Play 제출용 AAB는 별도 승인 전까지 새로 만들지 않았다.

### 17단계 — Play R8 최적화 지표 보강

Play Console의 앱 번들 최적화 화면에서 전체 모드와 기존 리소스 축소만 감지되고 코드
최적화 비율이 계산되지 않던 설정을 보완했다. AGP 8.12를 유지하면서 Google 권장 기본
파일을 `proguard-android-optimize.txt`로 바꾸고, 최적화된 리소스 축소와 클래스 재패키징을
활성화했다. 같은 설정이 Expo prebuild 뒤에도 유지되도록 전용 config plugin을 추가했다.

새 release AAB에서 `-dontoptimize`가 빠지고 `-repackageclasses`가 적용된 것, R8 mapping과
제거 목록이 생성된 것을 확인했다. 강화된 release APK는 SM-A165N에 설치해 정상 실행과
홈 화면 렌더링, 크래시 없음까지 확인한 뒤 동일 산출물의 AAB를 최종 업로드 파일로 교체했다.
